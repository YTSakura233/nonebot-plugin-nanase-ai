# MySQL/MariaDB表、事务与缓存

本包examples/schema.sql给出原创元数据表结构示例，使用utf8mb4、源站/地区/ID联合键、定数DECIMAL和具名notes JSON。它不自动执行，也不是ナナセ当前soruto_nb_knowledge表的迁移文件。

## 为什么必须区分来源

两个服务的song_id相同，不代表一条记录；同一首歌标准与DX也不应互相覆盖。历史谱面版本参与主键时，可以回溯某次成绩使用的定数。若只需要当前曲库，另建一个明确的current视图或在查询中限定版本，不能把历史记录直接全量排序当当前B50。

## 事务替换一个来源

先在事务外下载和解析，校验通过后开始事务；按来源键删除旧批次并插入新批次；提交成功后才切换内存索引。任意写入失败回滚。不要先清空正式表再发HTTP，也不要捕获异常后仍回复“更新成功”。

参数化示例应使用驱动占位符：

```python
await cursor.execute(
    'SELECT title FROM kb_song WHERE provider=%s AND region=%s AND source_song_id=%s',
    ('lxns', 'cn', song_id),
)
```

表名、列名需要程序白名单管理，不能把用户文本直接拼入SQL；占位符不能保护任意动态标识符。

## 缓存与版本

公开曲库适合落盘快照、ETag/Last-Modified与有限缓存；每次群聊查歌都重新下载全曲库没有必要。内存保存只读索引，更新完成后整体交换，避免半新半旧。授权个人成绩另用按主体与scope隔离的缓存，不放进共享曲库缓存。

本包只有JSON元数据、Markdown、离线索引和演示程序。真正数据库性能与索引长度、事务锁、连接池大小有关，不能仅凭示例表保证生产环境吞吐；本轮未连接用户数据库做迁移或压测。
